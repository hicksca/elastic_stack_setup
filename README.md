# elastic_stack_setup

A small Go CLI that stands up a self-managed Elastic Stack on a Mac using
[apple/container](https://github.com/apple/container), with TLS everywhere and
each node reachable over your Tailscale tailnet at its own `*.ts.net` name.

It is built for lab and support-reproduction work: pick a stack version, pick
how many Elasticsearch and Kibana nodes you want, and get a cluster that looks
like production (security on, HTTPS on the Elasticsearch REST layer, mTLS on
the transport layer) without hand-editing any config.

## What you get

Each node runs in its own lightweight VM on Ubuntu 26.04 from the official
Elastic tarballs. Every container joins your tailnet as its own machine and
obtains a Let's Encrypt certificate for its hostname through
`tailscale cert`, so `https://elastic-kibana-1.<tailnet>.ts.net:5601` and
`https://elastic-es-1.<tailnet>.ts.net:9200` are trusted by any browser or
client on the tailnet, with no self-signed warnings.

Tailscale runs in userspace-networking mode inside the containers, which
handles inbound tailnet traffic but cannot carry outbound traffic from
Elasticsearch or Kibana. Node-to-node and Kibana-to-Elasticsearch traffic
therefore stays on the apple/container network. Kibana gets `/etc/hosts`
entries that map each Elasticsearch hostname to its container IP, so it still
verifies the real Let's Encrypt certificate. The transport layer uses a private
CA generated by the CLI, because Let's Encrypt certificates no longer carry the
clientAuth EKU that Elasticsearch transport mTLS requires.

Each node's Tailscale state is persisted on the host, so rebuilding a cluster
reuses the same tailnet machines and cached certificates instead of
registering new ones.

## Requirements

A Mac running [apple/container](https://github.com/apple/container) with the
`container` CLI in your `PATH`. Apple silicon is assumed; the image also builds
on x86_64 if you have it.

A Tailscale tailnet with [MagicDNS and HTTPS certificates](https://tailscale.com/docs/how-to/set-up-https-certificates)
enabled, and the Mac you are working from joined to it.

A reusable Tailscale auth key (`tskey-auth-...`). Every node uses the same key,
so it must be reusable. An API access token (`tskey-api-...`) will not work.

Go 1.24 or newer to build the CLI.

## Usage

```sh
go build -o elastic_stack_setup .
export TAILSCALE_AUTHKEY="tskey-auth-..."

# single-node cluster with one Kibana
./elastic_stack_setup up -v 9.4.3 -t tailb7f31.ts.net

# three Elasticsearch nodes, one Kibana, 12 GB per ES node
./elastic_stack_setup up -v 9.4.3 -t tailb7f31.ts.net -e 3 --es-memory 12

# tear it all down
./elastic_stack_setup down
```

`up` builds the image, generates credentials and transport certificates, and
starts the containers. Certificate issuance and cluster formation continue in
the background after it returns. Follow along with:

```sh
container logs -f elastic-es-1
container logs -f elastic-kibana-1
container exec elastic-es-1 cat /var/log/tailscaled.log
```

Generated passwords are written to `elastic-deploy/credentials.txt`. Log in to
Kibana as `admin` (a superuser). `kibana_svc` is the account Kibana itself uses
to talk to Elasticsearch and holds the `kibana_system` role.

### Flags

| Flag | Default | Description |
| --- | --- | --- |
| `-v`, `--version` | required | Elastic Stack version, e.g. `9.4.3` |
| `-t`, `--tailnet` | required | Your tailnet DNS name, e.g. `tailb7f31.ts.net` |
| `-e`, `--es-nodes` | `1` | Number of Elasticsearch nodes |
| `-k`, `--kibana-nodes` | `1` | Number of Kibana instances |
| `--es-memory` | `8` | Memory per Elasticsearch VM in GB; the JVM heap is half |
| `--kibana-memory` | `4` | Memory per Kibana VM in GB |
| `--workdir` | `./elastic-deploy` | Where build files, certs, state and credentials live |
| `-c`, `--cluster` | `elastic` | Name prefix for containers and tailnet hostnames |

The `--cluster` flag applies to both `up` and `down`. Nodes are named
`<cluster>-es-N` and `<cluster>-kibana-N`, and that name is also the tailnet
hostname. Run several clusters side by side by giving each a different name.

### Ports

Each node is also published on the Mac's loopback: Elasticsearch nodes on
`9200`, `9201`, ... and Kibana on `5601`, `5602`, .... The certificates are
issued for the tailnet names, so expect a hostname mismatch warning when using
`localhost`; the tailnet URLs are the intended way in.

## Layout

```
main.go                 Cobra CLI: image build, cert generation, container orchestration
assets/Containerfile    Ubuntu 26.04 + Tailscale + Elasticsearch and Kibana tarballs
assets/ts-up.sh         Joins the tailnet and fetches the node's Let's Encrypt cert
assets/start-es.sh      Elasticsearch entrypoint: config, users, discovery, launch
assets/start-kibana.sh  Kibana entrypoint: config, host mappings, launch
```

The `assets` directory is embedded in the binary with `go:embed` and written
out to `elastic-deploy/build` on each run.

`elastic-deploy/` is created at runtime and holds the generated credentials,
the transport CA private key, and each node's Tailscale machine keys. It is
listed in `.gitignore` and should stay out of version control.

## Things worth knowing

Let's Encrypt issues at most five certificates per exact hostname per week.
Because state is persisted per node, normal rebuilds reuse the cached
certificate and do not count against this. If a hostname does hit the limit,
tailscaled's ACME client silently sleeps until the window reopens, which
appears as `tailscale cert` hanging. The start script bounds each attempt to
three minutes and retries, and the quickest fix is a fresh hostname via
`--cluster`.

If a machine with the same name already exists in the Tailscale admin console
and the node has no persisted state for it, Tailscale appends a suffix
(`elastic-es-1-1`). The start script detects the mismatch and exits with a
message rather than issuing a certificate for the wrong name. Delete the stale
machine and run `up` again.

Multi-node clusters run Elasticsearch in production mode, which enforces
bootstrap checks such as `vm.max_map_count >= 262144`. The start script tries
to set it and warns if it cannot; check the VM's default with
`container exec elastic-es-1 cat /proc/sys/vm/max_map_count` if a node fails
its bootstrap check.

Discovery for additional Elasticsearch nodes is seeded from the container IPs
of nodes already running, and Kibana's host mappings are baked in at start
time. If container IPs change after a VM restart, run `down` and `up` again.

Data directories are not persisted. `down` destroys the cluster and its
indices. Credentials and the Tailscale auth key are passed to containers as
environment variables, so they are visible in `container inspect`; treat this
as a lab tool, not a production deployment.
